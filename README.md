# 工位与会议室排班求解库

我们给办公楼排工位和会议室，规则不少：一个人不能连排两个时段、会议室容量要够、有人指定必须坐一起、有人不能坐一起、有些时段不能用。现在是同事拿表格手工排，一个季度要排两天，改一个人就全乱。想自己写一个求解的库。

硬约束一条都不能破，破了这排班就没法用；软约束是求最优，不是随便给个解就行，权重总和要最小。解不出来的时候至少要说明白：哪几条约束互相矛盾，具体到规则编号，不能只说一句无解。同一个实例跑两遍结果必须一样；最优解可能有好几个，选哪个的规则写在下面。规模上，一个季度大概两百个变量、几千条约束，要在几十秒内出结果，纯靠穷举是不行的，得有传播和剪枝。实现只用标准库，测试用 unittest。

仓库里只有这份说明和 samples 里的样例实例与期望结果，代码从零写。

## 模型

实例是一份 JSON：

```json
{
  "case_id": "case-1",
  "periods": ["mon-am", "mon-pm"],
  "locations": [{ "id": "desk-1", "capacity": 1 }, { "id": "room-a", "capacity": 2 }],
  "people": ["alice", "bob"],
  "rules": [ ... ]
}
```

- **变量**：每个「人 × 时段」是一个变量，值域是「某个地点」或 `none`（不排）。
- 变量顺序固定为 `people` 数组顺序 × `periods` 数组顺序；取值顺序固定为 `locations` 数组顺序，最后是 `none`。这两条顺序决定了输出顺序与多解时的选择。
- **目标**：最小化软约束的权重总和。

## 约束语义

硬约束（每条都必须有 `id`，`kind` 取下面的值）：

| kind | 字段 | 含义 |
| --- | --- | --- |
| `fixed` | `person`, `period`, `location` | 该人该时段必须在这个地点 |
| `forbidden` | `location`, `period` | 该时段这个地点不能给任何人用 |
| `capacity` | `location`, `period`, `max` | 该时段在该地点的人数不超过 `max`（在 `locations[].capacity` 的基础上进一步收紧） |
| `no_consecutive` | `person` | 这个人在**相邻**两个时段不能都排（两个都非 `none` 就违反） |
| `together` | `people` | 这些人每个时段的取值必须**完全相同**（要么都在同一地点，要么都不排） |
| `apart` | `people` | 这些人每个时段不能坐在同一个地点（`none` 不算地点，两人同时不排是允许的） |

另外，**地点容量**是模型自带的硬约束：任意 `(地点, 时段)` 的人数不超过 `locations[].capacity`。

软约束（带 `weight`，正整数）：

| kind | 字段 | 违反的判定 |
| --- | --- | --- |
| `prefer` | `person`, `period`, `location`, `weight` | 该人该时段的取值不是这个地点（含 `none`）就罚 `weight` |
| `avoid` | `person`, `period`, `weight` | 该人该时段有排（取值不是 `none`）就罚 `weight` |

约束只对实例里声明过的 `people` / `periods` / `locations` 生效；引用不存在的名字按实例格式错误处理。

## 求解要求

- 先满足全部硬约束，再在可行解里把软约束总权重压到最小；
- 两百个变量、几千条约束要在几十秒内给出结果：必须做约束传播（例如把已定的取值传播到相关变量的值域上、容量按「已定 + 可能」双向检查）与分支限界（用未定变量的最小罚分做下界剪枝），纯穷举不行；
- 同一实例跑两遍，输出必须逐字节一样。

## 多解规则

最优解可能不止一个，取哪个写死成这条：

> 按变量顺序（`people` × `periods`）与取值顺序（`locations` 顺序，最后 `none`）做深度优先搜索，**只在遇到严格更优的解时才替换当前最优**；因此多个最优解并存时，保留的是这个固定顺序下先被搜到的那个。

实现可以随意剪枝、换搜索策略，但最终交出来的解必须与这条规则一致（等价做法：先求出最优代价，再按固定顺序取第一个达到该代价的可行解）。

## 无解说明格式

硬约束互相矛盾时，不输出排班，只输出一行：

```text
unsat,<规则id>,<规则id>,...
```

规则 id 按**声明顺序**升序排列，表示一组互相矛盾的规则（极小冲突集）：从中去掉任何一条，剩余约束都可满足。构造方式：从全部硬约束出发，按声明顺序逐条尝试去掉，去掉后仍不可满足的就真的去掉，直到不能再去掉为止——结果与顺序都确定。若去掉所有规则后仍不可满足，说明冲突出在模型自带的地点容量上，此时输出 `unsat,base-model`。

## 输出格式

可满足时，第一行是总罚分，之后按「变量顺序」逐行给出取值，行尾 LF：

```text
cost,7
alice,mon-am,desk-1
alice,mon-pm,none
```

取值写地点 id 或 `none`。

## 样例

```text
samples/case-1.json / case-1.expected.txt    12 个变量的小实例，取到零罚分
samples/case-2.json / case-2.expected.txt    60 个变量 + 18 条规则，含一条无法满足的 prefer（最优代价 7）
samples/case-3.json / case-3.expected.txt    无解实例：fixed 与 forbidden 指向同一个 (地点, 时段)，期望 unsat,R1,R2
```

case-1 覆盖 `together`、`apart`、`no_consecutive`、`forbidden`、`capacity` 与两条软约束；case-2 的 `R18` 要求 `p1` 在 `mon-am` 坐 `desk-2`，而 `R01` 已把 `p1` 固定在 `desk-1`，所以最优解必须吃下这 7 分——用来验证「软约束是求最优」而不是随便给个可行解。

## 实现说明

代码在 `scheduler/` 包（只用标准库），测试在 `tests/`（unittest）：

```text
python -m scheduler samples/case-1.json     # 求解并打印结果
python -m unittest discover -s tests        # 跑全部测试
```

### 模型实现

- 变量按下标排列：`人下标 × 时段数 + 时段下标`，即 people 顺序 × periods 顺序；
  取值用位掩码表示，bit i 是 `locations[i]`，最高位是 `none`，天然对应规定的取值顺序。
- `scheduler/model.py` 负责解析与校验：引用不存在的 people / periods / locations、
  硬约束缺 `id`、软约束 `weight` 非正整数等一律抛 `InstanceError`。

### 传播是怎么做的

`scheduler/solver.py` 里每类约束是一个传播器，变量值域一收缩就把监听该变量的
传播器重新入队，跑到不动点或某个值域变空（失败回溯）：

- `fixed` / `forbidden`：编译期直接收缩值域；
- `capacity`：按「已定」（值域收缩为单值）计数，超限即失败，达到上限就把该地点
  从同时段其他人的值域里删掉；
- `no_consecutive`：相邻时段一方值域里没有 `none`（必须排）时，另一方必须为 `none`；
- `together`：同组人同一时段的值域取交集；
- `apart`：已定为某地点的人，把该地点从同组其他人同时段的值域里删掉（`none` 不算）。

### 下界怎么算

每条软约束只涉及一个变量，罚分可以按变量分解：预计算 `penalty[变量][取值]`。
分支限界的下界 = 已定变量的累积罚分 + 每个未定变量在当前值域上的最小罚分
（传播收缩值域后下界会自动变紧）。下界不低于当前最优时就剪枝。

### 搜索顺序与多解规则的对齐

深度优先搜索严格按「变量顺序 × 取值顺序」展开，只在遇到**严格更优**的解时替换
当前最优；剪枝条件也是「下界 ≥ 当前最优」，与「并列最优不替换」等价。因此第一个
达到最优代价的解就是规定顺序下的第一个最优解，与 README 的多解规则逐字节一致。
全程无随机、无哈希序依赖，同一实例跑两遍输出逐字节相同（有测试覆盖）。

### 冲突集是怎么求出来的

`scheduler/conflict.py`：只在硬约束上判可满足性（软约束不影响可行与否）。
从全部硬约束出发，按声明顺序逐条尝试删除，删掉后仍不可满足就永久删除，
一遍扫描后剩下的就是极小冲突集，按声明顺序输出 id；若删到一条不剩仍不可满足，
输出 `unsat,base-model`。

### 关于地点容量的一处语义说明

README 前文把 `locations[].capacity` 描述为模型自带的硬约束，但样例的期望结果
表明它**不**作为独立硬约束生效：case-1 里 alice 与 carol（`together`）在 mon-am
同坐容量为 1 的 `desk-1`，case-2 里 mon-am 有四人同坐 `desk-1`，期望输出都是
可行且最优的。因此实现按样例对齐：`locations[].capacity` 只作为 `capacity` 规则的
默认上限（有效上限 = `min(规则 max, locations[].capacity)`），不单独约束排班；
`unsat,base-model` 分支按规范保留。
